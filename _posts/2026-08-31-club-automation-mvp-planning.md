## 들어가며 (Situation)

대학 동아리와 소규모 조직에서 반복되는 업무를 자동화하는 개인 MVP 프로젝트를 시작했다.

개인 우선순위 일정에 밀려 동아리 업무가 계속 후순위로 밀리는 게 문제였다. 문제는 "밀린다" 자체가 아니라, 밀린 업무를 처리할 때마다 매번 상황 파악에 시간을 다시 쓴다는 점이었다. 이 반복되는 후순위 업무를 줄이기 위해 자동화 도구를 직접 만들어보기로 했다.

## 문제 상황 (Task)

개발을 시작하기 전에, 먼저 아래 세 가지를 정리해야 했다.

1. **기획안을 상세하게 작성하는 것** — 무엇을 자동화할지 범위를 명확히 하지 않으면 개발 방향이 흔들린다.
2. **Word로 작성된 기존 업무 메뉴얼을 컴퓨터가 읽을 수 있는 형태로 바꾸는 것** — 자동화 로직이 참고할 원본 자료가 사람만 읽을 수 있는 Word 문서 상태였다.
3. **개발 착수 전 필요한 사전 작업을 끝내는 것** — 코드를 먼저 짜지 않고, 무엇을 만들지 문서로 먼저 확정하고 싶었다.

## 해결 과정 (Action)

개발 시작 전 사전 작업을 아래 순서로 진행했다.

```mermaid
flowchart LR
    A[기획안 작성] --> B[기존 Word 메뉴얼 확보]
    B --> C[민감 정보 마스킹]
    C --> D[Markdown으로 변환]
    D --> E[JSON 구조 초안 작성]
    E --> F[PRD 작성]
    F --> G[개발 착수 - 예정]
```

| 단계 | 진행 상태 |
|---|---|
| 기획안 작성 | 진행 중 |
| 예시 메뉴얼 마스킹 | 완료 |
| Word → Markdown 변환 | 완료 |
| JSON 구조 초안 작성 | 완료 |
| PRD 작성 | 완료 |
| 개발 착수 | 시작 전 |

**Word 메뉴얼 마스킹 후 Markdown 변환**

기존 동아리 업무 메뉴얼은 Word 파일이었다. Word 파일은 사람이 읽기엔 편하지만, 이후 프로그램이 내용을 파싱하기엔 적합하지 않다. 그래서 먼저 문서 안의 이름·연락처 같은 민감 정보를 마스킹(익명화)해 예시용 메뉴얼로 만든 뒤, 이를 Markdown 형식으로 옮겼다. 이 과정에서 AI를 활용해 변환 작업의 초안을 뽑았다.

민감 정보를 먼저 마스킹한 이유는, 앞으로 이 예시 메뉴얼을 기획안이나 개발 참고 자료로 계속 재사용할 예정이기 때문이다. 원본을 그대로 쓰면 공유할 때마다 다시 걸러내야 해서, 처음부터 마스킹된 버전을 기준 자료로 삼기로 했다.

**JSON 구조 초안 작성**

Markdown으로 옮긴 메뉴얼 내용 중, 프로그램이 실제로 참조해야 할 정보(예: 업무 항목, 담당, 처리 순서 같은 값)는 JSON으로 별도 구조화했다. JSON을 처음 작성해봤는데, Markdown이 "사람이 읽기 좋은 형태"라면 JSON은 "프로그램이 읽기 좋은 형태"라는 차이를 이번에 체감했다.

**PRD 작성**

기획안과는 별도로 PRD(제품 요구사항 문서)도 작성했다. 기획안이 "왜 이 프로젝트를 하는가"를 정리한 문서라면, PRD는 "무엇을 어떤 조건으로 만들 것인가"를 더 구체적으로 못박는 문서로 구분해서 썼다.

이 세 작업(Markdown 변환, JSON 초안, PRD) 모두 AI를 활용해 초안을 만들고, 그 결과를 직접 검토·수정하는 방식으로 진행했다.

## 결과 (Result)

- 마스킹 처리된 예시 동아리 메뉴얼 1건을 Word에서 Markdown으로 변환 완료
- 위 메뉴얼을 기반으로 한 JSON 구조 초안 1건 작성 완료 (처음 작성해본 JSON)
- PRD 초안 1건 작성 완료
- 기획안은 아직 상세 작성 진행 중이며, 코드 개발은 아직 시작하지 않음

아직 개발 이전 단계라 성능 수치 같은 지표는 없지만, "문서만 있고 구조화되지 않은 상태"에서 "프로그램이 참조 가능한 형태(Markdown + JSON)"로 원본 자료를 옮겼다는 점이 이번 단계의 실질적인 결과다.

## 더 학습하면 좋은 개념

- **JSON Schema** — 지금은 JSON을 자유 형식으로 작성했지만, 구조가 커지면 필드 누락이나 타입 오류를 잡기 어려워진다. JSON Schema로 구조를 미리 정의해두면 이후 개발 단계에서 데이터 검증이 쉬워진다.
- **Markdown 명세 (CommonMark)** — Word에서 Markdown으로 변환할 때 "어디까지가 표준 문법인가"를 알아야 변환 결과가 여러 도구에서 깨지지 않는다.
- **PRD(제품 요구사항 문서) 작성 방법론** — 기획안과 PRD의 역할을 더 명확히 나누는 법을 배우면, 이후 기능이 늘어나도 "왜 만드는가"와 "어떻게 만드는가"가 섞이지 않는다.
- **데이터 마스킹/익명화 원칙** — 이번엔 이름·연락처 정도만 가렸지만, 조직 데이터를 계속 다루게 될 프로젝트라면 어떤 정보까지 가려야 하는지 기준을 세워두는 게 필요하다.
